# Rebase notes — 2026-07-19: local Phases 4–5 onto origin/main (v2.6.14)

Local `main` (built against v2.6.9) had diverged from GitHub: 33 remote commits
(v2.6.10 – v2.6.14, built in web sessions) vs 5 local commits (plan docs, playlists
Phase 4, playlists Phase 5). This documents how the rebase was resolved and what, if
anything, was lost.

**Outcome: no losses.** Every local change survived (ported where the remote layout
changed); every remote change was preserved. Verified by the full gates — 437 backend
tests, ruff, tsc, production build — plus a live boot (login with the new username
field, Run page with the FORCE TEMPO toggle, Settings with the Run-users panel and
Background-sync interval, no console errors).

## The structural conflict: `db.py` → `db/` package

Remote commit `6ecaf92` split the 1.8k-line `bpm_tagger/db.py` into a `db/` package
(`base/tracks/grabber/playlists/suggestions` mixins). Both local phases modified the
old monolith, producing modify/delete conflicts. Resolution: take the deletion, port
the diffs to the new modules —

| Local change (old `db.py`) | Ported to |
|---|---|
| Phase 4: `add_local_playlist`, `_refresh_local_track_count`, `add_track_to_local_playlist`, `remove_playlist_track` | `db/playlists.py` |
| Phase 5: `players` + `player_playlists` tables (`_create_player_tables`) | `db/base.py` (called from `_migrate`) |
| Phase 5: player CRUD / scoping methods | **new** `db/players.py` (`PlayersMixin`, added to `BPMDatabase` bases) |
| Phase 5: `_queued_pt_ids` + queued-state reads in `list_playlists` / `get_playlist_tracks`; `delete_playlist` cascade | `db/playlists.py` |
| Phase 5: `enqueue_grab` normalized-key dedupe for no-Spotify-id tracks | `db/grabber.py` (import adjusted to `..grabber.matching`) |

One comment was corrected during the port: remote v2.6.10 turned SQLite FK enforcement
ON, so the Phase 5 "FKs are off in this codebase" rationale became wrong. The player
join table still carries no FK constraint (the `playlists` table can be rebuilt by the
legacy migration), so the Python-side cleanup stays — the comment now says that.

## Textual conflicts and how each side won

- **CHANGELOG / DOCKERHUB_README** — both sides prepended entries; kept remote's
  v2.6.10–v2.6.14 entries *and* the local Unreleased (Phase 4 + 5) entries above them.
- **README env-var table** — kept remote's `UI_FORCE_SECURE_COOKIE` row + local's
  updated `RUN_PASSWORD`/`RUN_SESSION_DAYS` text and new `RUN_FORCE_TEMPO` row.
- **README security section** — kept local's player-role + per-user-scoping bullets,
  restored remote's stronger SSRF wording (redirects not followed).
- **`Run.tsx`** — the hard one. Remote rebuilt the page (one-screen mobile layout,
  cover slot, single-slot floating status pill replacing stacked banners, source picker
  moved off the cover into the Queue view). Local Phase 5 had edited the *old*
  structures. Resolution: remote structure wins everywhere; local semantics grafted on:
  - the old cover `sourceOverlay` and `buildMessages` blocks were **dropped as
    superseded** (their Phase 5 payloads — `fullAccess` gating of the Whole-library
    option, status text — live on in the surviving `sourcePicker` and `statusNote`).
  - the `forceToggle` control was re-inserted into the new desktop cockpit controls
    and the mobile column (hidden in tap/queue modes, as designed).

Auto-merged-but-sensitive files (`web/app.py` allowlist vs. admin-only healthz,
`web/api/run.py` scoping + force-tempo vs. playlist top-up/dimming, `settings.py`,
`main.py` PeriodicSync startup) were reviewed by hand and are covered by the merged
test suites from both lines.
